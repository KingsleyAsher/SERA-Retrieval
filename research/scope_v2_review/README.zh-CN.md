# scope-v2 修订与独立回审入口

[English](README.md) | [简体中文](README.zh-CN.md)

此目录提供历史 scope-v1 的两个反例、scope-v2 的修订实现及虚构夹具检查，便于对修复版本进行独立审查。**独立实现回审尚未完成**；本包中的执行者检查及发布时复验不能替代独立审查。

## 精确对象

- 修订实现：[scope_engine.py](阶段三第四部分定点修订-2026-10-30/scope_engine.py)，原始 SHA-256 `fd6b28bbe6ee00cfd75259ee4bf553db9a9c2881c494a7a55bd27c27a39fb3cd`。
- 对照实现：[scope-v1 scope_engine.py](阶段三-合法范围成本诊断/scope_engine.py)。两版使用随包提供的[历史框架](阶段二/framework.py)，来源哈希与修订清单声明的依赖一致。
- 选择器分别位于两个版本目录。为了不隐式访问私有数据，公开副本取消了默认私人目录，调用方必须显式指定隔离夹具目录；除了这个入口保护，算法未改。源文件和公开副本各自的哈希列于 [provenance.json](provenance.json)。
- [修订契约](阶段三第四部分定点修订-2026-10-30/修订契约.json)、[修前反例](阶段三第四部分定点修订-2026-10-30/probe-before.json)及[修后结果](阶段三第四部分定点修订-2026-10-30/probe-after.json)只包含虚构测试结果。

## 需要审查的两个修复

1. 原实现成功返回时，数据库持久化的是 `commit` 而不是 `done`，恢复可能再次索要提交额度。修订构造终态副本，在成功保存后才同步内存状态；预算不足或观测到 SQLite 写锁失败时不得伪造终态，已发生的提交尝试不退款。已验证范围是相同请求与快照、依赖有效的恢复；不证明断电、进程崩溃或提交结果不确定时的恰好一次。
2. 原选择器的 `max(10,total//10)` 存在向下取整和隐含至少 10 个成员的问题。修订使用 `total > 0`、`10*count >= total` 和 `4*count <= 3*total`；接近一半使用整数距离，合法短范围不得被隐藏门槛排除。

原审查反例及修订检查均为虚构数据。历史记录称两项反例由观察到缺陷变为未观察到，并有四组定点和六组继承检查；发布准备时在隔离临时副本中运行了原反例、修订检查和继承检查，均通过。此次复验不是独立审查，不重测私人数据，也不证明全局正确性或性能。旧性能结果只属于 scope-v1，不能转贴给 scope-v2。

独立审查可从 `review-probe-original.py`、`verify_revision.py` 和 `checks.py` 入手。它们使用临时 SQLite 和虚构数据；后两者会写入自身所在目录，因此应先复制整个目录到临时位置后运行。依赖版本见仓库根目录的 `requirements.txt`。未经审查，不应在生产系统中直接复用。
