# 阶段三第二部分实现说明

[English](实现说明.en.md) | [简体中文](实现说明.md)

本目录独立于上一部分，旧原型和结果不覆盖。`execution_engine.py` 从上一部分冻结的执行器派生，保留评分、来源、提交、预算和接续语义；匹配改为可替换的 CandidateBank，增加种子评分、粗分区评分和可持久化的访问前沿。协议先于实测冻结。

紧凑缓存使用 f64 查询数组与 int64 ID/版本数组；JSON 对照保持同一匹配规则。两者均读取整个候选库的逻辑载荷，紧凑路径包含矩阵复制及种子复制成本，不把查询时转换藏入初始化。字节大小是载荷，未包含 Python 对象和分配器。

IVF 是小型可控制参考执行器，KMeans 建立倒排表。冷顺序按当前查询与中心的内积，热顺序以该值和合法种子在当前查询下的已观察分数取最大值。两者使用相同总规范评分预算，种子计入；未启用任何几何界剪枝。只有不同预算下达到实际可比较质量，才能讨论少访问；相同预算仅改变质量，不自动构成访问量降低。

预算中断可通过继承 Store.save/restore 保存 Execution。选中种子内容、验证／评分游标、粗顺序、表游标、表内游标和累计消耗均保留。原生 ANN 内部硬上限仍不支持。所有结果为近似或完整规范评分下的枚举参考，不发严格证书。

开发简查中曾有一个测试把“紧凑表示一定更小”套用到只有两个简单坐标的虚构条目；该假设不成立（文本里的 0/1 很短），已移除这个不合理断言，保留选择与载荷等价检查。真实 1024 维载荷大小由实测报告决定。测试异常时的 SQLite 关闭顺序也改为上下文管理。该记录不是算法失效或性能实验。
